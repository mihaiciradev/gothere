## Configuration

Validated at first use by `src/infrastructure/env.ts` (Zod). Missing or invalid values fail fast with every problem listed. Documented in `.env.example`.

| Variable | Required | Purpose |
| --- | --- | --- |
| `APP_ENV` | default `local` | Safety guards and cookie security |
| `LOG_LEVEL` | default `info` | Structured logger threshold |
| `DATABASE_URL` | yes | Postgres connection (Neon: pooled URL, `sslmode=require`) |
| `DATABASE_POOL_MAX` | default 5 | Per-instance pool size; keep small on serverless |
| `BETTER_AUTH_SECRET` | yes, ≥ 32 chars | Session signing/encryption |
| `BETTER_AUTH_URL` | yes; https in production | Canonical origin; only trusted origin |
| `TEST_DATABASE_URL` | tests | Local `*_test` database |
| `SEED_DEMO_PASSWORD`, `SEED_ADMIN_PASSWORD` | seeding | Demo account passwords (≥ 12 / ≥ 16 chars) |

Introduced later: `ANTHROPIC_API_KEY`, `AI_MODEL_FAST`, `AI_MONTHLY_BUDGET_MINOR` (M3); `OPERATIONS_SECRET` (M1, jobs/cron); `SENTRY_DSN` (M4).

## Database

- Schema: `src/infrastructure/db/schema/*.ts`. Migrations: `drizzle/` (generated SQL, committed, never edited after being applied).
- Change flow: edit schema → `pnpm db:generate --name <change>` → review SQL → `pnpm db:migrate` locally → commit both. CI runs `drizzle-kit check`.
- Hand-written SQL (triggers, functions) goes in `drizzle-kit generate --custom` migrations.
- Neon provisioning (needs CTO approval): one project, `main` branch for production, a branch per preview; two roles: `gothere_migrator` (DDL) and `gothere_app` (DML only). Migrations run from CI or a trusted machine, never at request time.

## Seed data

`pnpm db:seed` (idempotent, refuses production) creates the fictional ecosystem from `scripts/seed-data.ts`: 6 users (2 attendees, 3 organizer members across 2 tenants, 1 platform admin), 2 organizations, 3 published events, 5 experiences, 10 inventory items. Users are created through Better Auth so passwords are hashed exactly as in production.

Strategy for later milestones: historical orders, tickets and demand signals are generated by running the real M1/M3 services in a seeding mode and are stamped `origin = 'seed'`, so analytics can always separate seeded history from live activity and seeded data never bypasses invariants. The sold-out *Sunset Sessions* state and the ~384-person unmet-demand signal are produced this way, not by writing counters directly.

## Background jobs

Design (implemented with the first job in M1): a `jobs` table with `status`, `run_at`, `attempts`, `max_attempts`, `locked_until`, `locked_by`, `last_error`, `idempotency_key`. Workers claim with `UPDATE … WHERE id = (SELECT id … FOR UPDATE SKIP LOCKED LIMIT n) RETURNING *`, set a lease, and retry with exponential backoff. Expired leases are re-claimable, so interrupted serverless executions recover. Triggers: Vercel Cron (subject to plan limits) and a protected manual endpoint (`OPERATIONS_SECRET`) for local runs and demos. Reservation expiry is also enforced lazily on read so correctness never depends on the scheduler.

## Incidents (M4)

Severity: P0 critical production/security · P1 major degradation · P2 limited issue · P3 minor. Severity never widens autonomous permissions. Incidents are deduplicated by fingerprint, carry correlation ids, technical and commercial impact, and a sanitized diagnostic report suitable for an external coding agent. Generated investigation packages are labelled distinctly from investigations actually executed.

## Observability

Structured JSON logs via `src/infrastructure/logging/logger.ts` with secret redaction. Correlation ids are added per request in M1. Sentry is introduced in M4.
